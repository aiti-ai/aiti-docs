Why a Web Workbench (aiti-agent)

In one line: move the actions you repeat dozens of times a day — start a task, watch progress, review output, switch models, read statistics, take over from another device — out of an IDE window or a terminal, onto an always-on operating surface that is remote-capable and mobile-capable, while the code, the sessions and the tools stay on your own machine.

First, a warning: this may not be for you

If you only use AI occasionally, do not bother with this — use what you already know: IDE-embedded AI, a CLI agent, a desktop app, all get work done. Tools are not good or bad; the one you can drive is the good one.

This project is customized around my own working habits and scenarios. It may not be a fit for you. See Origin.

A 30-second check

How many of these five happened to you last week?

QuestionTypical pain point of other form factors
Two or more agents open at once (pi / Claude Code / Codex / Cursor…), hopping windows to find contextIDE and CLI each keep their own history; context breaks when you switch tools
You wanted to check progress from a phone, but had to SSH in or wait to get back to the laptopTerminal / IDE mobile is mostly view-and-approve; full operation waits for the laptop
You closed the local IDE or terminal and worried the agent would be interruptedLocal agents follow the window (cloud agents are the exception)
You wanted "how many tokens this month, which model is most expensive" and could only read a billNo cross-agent cost data plane
You wanted the AI to look at the page, click elements and change styles, so you took a screenshot and pasted itTerminals and editors cannot see what is rendered

Two or more "yes" means your workflow has outgrown a single-window tool — which is exactly what a web workbench is designed around. Below: a form-factor comparison, then the mechanics and the boundaries. Every claim is verifiable in the ten-minute self-test at the end.

Zero or one "yes": close this page and keep using what you have — there is no reason to change your workflow for a workbench.

Scope: this page compares form factors, not specific products. Within one form factor the spread is wide (Cursor and JetBrains AI are both IDEs but differ a lot). Cells describe typical capability: ✅ native / ⚠️ partial or via plugins / ❌ essentially absent. Every "N" below is today's built-in coverage, not a capability ceiling.

The real difference is not "does it have a web page" but whose runtime sits behind the browser. A thin shell is just a display layer; a mature self-hosted web UI has a runtime too, but usually serves one agent family. The web-workbench bar is: runtime, sessions, queues, tools and statistics in your own service — and across agents.

2. The big comparison

Three things to keep in mind so the tables are not misread:

  1. ✅ / ⚠️ / ❌ describe the form's out-of-the-box default. ⚠️ = usually needs a plugin, MCP, a cloud service or your own extension to reach parity; ❌ = no general extension point reaches the same level — not "impossible forever".
  2. Other ecosystems are not weak: IDEs have marketplaces + MCP + ACP, CLIs have plugins / skills / hooks / MCP, desktops have MCP extensions and connectors, and self-hosted web shells are growing. The gap is ownership and tool surface, not "whether plugins exist".
  3. Our "N" numbers are not closed lists either — they are today's built-in coverage, and they keep growing; see 2.0.

These differences only mean the existing tools did not cover how I work — not that they cannot or do not do it well. Each has its strengths; I just filled in the part I needed.

Missing capability has a path: install an MCP server, install a pi plugin, or write a workbench extension against the extension API (slots / services / API routes / agent hooks). The first two work as soon as they are installed; an extension can use existing slots, and if none fits, add one more extension point.

Scope note: modern IDE agents often run partly in the vendor cloud (Cursor Cloud Agents, Copilot coding agent), and Claude Code / Codex have cloud sessions and mobile apps. The tables count those under the respective form rather than as "web-only".

2.6 Beta and planned extensions (🟡 internal beta / 📋 planned)

These extensions are still in the experimental area; interfaces and behavior may change. They are listed to show how far the workbench can grow, not as a delivery promise. 🟡 means testable now; 📋 means still in design review and not implemented.

  • CodeHub (aiti-codehub) — one hub for work items and repositories across Yunxiao / GitHub / Gitee / GitLab: search, detail, comments, clone, create branch / merge request; multiple accounts; aiti_codehub_* tools + skills. Why it matters: brings "requirement → branch → session" into one workbench; code hosting is no longer another browser tab.

  • Video Studio (aiti-video-studio) — write a scene.json script → deterministic replay recording → TTS narration → ffmpeg composite; cursor / overlays / transitions / subtitles / multiple languages / 9:16. Why it matters: AI only participates while authoring, zero AI at runtime; demo videos become a repeatable pipeline instead of manual screen recording and editing. See the extension page.

  • Model Gateway (aiti-model-gateway) — exports models already configured in the workbench as an OpenAI-compatible API (chat/completions + tools, models, images); external CLIs connect with a gateway token. Why it matters: running other agents can share not only sessions but also models and credentials; external agents never see the real provider key.

  • Updater (aiti-updater) — version check → upgrade trigger → in-place observation (SSE) → jump to service management (stop / restart / unregister / env / logs); service registration, upgrade and service management in one place, with install and reverse proxy handled through the service-tunnels config. Why it matters: deployment, upgrades and service management become a panel in the workbench.

  • Proc Tree (aiti-proc-tree) · 📋 planned — roots at the pi-web host and lists every derived child process as a tree: terminals (aiti-cmd), tunnels (service-tunnels), subagents, external agents (Pi TUI / ACP backends) and detached sessions are all attributed; CPU / memory / uptime per row, and you can stop one process or a whole subtree, shaped like Chrome's task manager. Why it matters: no more digging through ps for a runaway child. Currently in design review, not implemented.

🟡 internal-beta extensions ship from the experimental area only, are not on npm, are not in releases, and upgrades may break compatibility; CodeHub's write operations (such as creating merge requests) are off by default. 📋 planned items are still in design review and not implemented.

3. Eight structural reasons

1. Runtime location: sessions live in the service, not in a window

The browser is only a view. Close the tab, lose the network, switch devices — the agent keeps running (vendor cloud agents can also run in the background; the difference is that they run in a vendor sandbox, not on your machine). Stopping or restarting pi-web itself does not have to interrupt the turn in flight either — detach hosts the agent in a standalone wrapper (Linux systemd-run, macOS plain detached process, Windows Win32_Process.Create) that talks to the service over a local socket and keeps a 4 MB ring journal: after a service restart you reconnect and the output replays exactly. Wrappers with no attached client and no output for the idle window are reaped. Already supported: pi, all ACP backends, Claude Code, CodeBuddy, Cursor, Qoder, omp and more; the rest are landing progressively. See Architecture · sessions and detachment.

2. Sessions as an asset: one index over 20+ agents

session-manager parses 23 agent families' private stores into one model (built-in coverage; third parties can add more through the session-agent-source slot), with FTS5 trigram search that works for Chinese, tags, favorites, archive snapshots, kanban and branch / worktree grouping in one sidebar. The AI can search too: pi-session-search gives the agent session_search / session_read, so after compaction it can read back the original messages and continue. History is not a fossil — open it and keep talking.

3. Input is a workflow

Local favorites / history hits render instantly as ghost text at zero model cost; only a miss goes to the AI continuation (OS dictation or completion plugins can cover part of it, but rarely put completion, commands, drafts and queues into one chain). Typing "model" or "compact" executes a command and returns the cursor to the composer. Press-and-hold gives streaming ASR with hotwords. Drafts are shared per session and survive crashes. The queue is persisted server-side: reorder, steer, take back to edit, and decide item by item after a restart. See aiti-ai-input, aiti-draft-keeper, aiti-queue-keeper.

4. Messages are interface objects

Paragraphs, headings, table rows and code lines are clickable: copy, quote, A/B options, highlight the line. The anchor banner tells you which prompt produced what is on screen; the navigation bar jumps to previous / next / earliest / latest. Long answers can switch into read-aloud mode with sentence-level highlighting. See aiti-msg-smart, aiti-ai-speek.

5. The toolchain lives on the same page

A real PTY terminal (survives restarts), container panel, virtual desktop VNC / RDP, service tunnels, files / Office / document center, git review and change lineage, JVM and Windows process debugging, subagent fleet, scheduled tasks, IM remote control — all panels in the same workbench, sharing the workspace and runtime context with the session. That is what "richer than an IDE" means concretely: not more editor features (IDEs still go deeper on editing and debugging), but a wider range of things the agent can act on.

6. Statistics and governance need to be centralized

Usage reports pivot over any dimension combination (workspace / provider / model / key / hour / date / agent) × multiple metrics, with three views and CSV export; external agent tokens are ingested too (third-party tools such as ccusage aggregate part of CLI usage, but not as a multi-dimensional view from the same runtime sessions). Add 16 provider balance and quota adapters, model health probes, context and smoothness indicators, per-session export, plus secret masking / vault / config rollback / data snapshots. See aiti-ai-usage.

7. A full-power small screen, not a reduced one

A phone is not a remote peephole: a touch composer matrix (model / thinking level / tool preset / compact / queue / extension state in one sheet), collapsible composer and queue, dialogs that go full screen and close with the system back gesture, right-panel state restore, touch drag reordering, voice plus a "⏎ newline" pill, read-aloud follow mode. PWA install and offline support are still on the roadmap — that is a known gap. See full mobile adaptation.

8. The page is the AI's scene (aiti-devtools)

Inject the debug client into the page you are developing: pick an element and structured information goes straight to the AI; the AI can run DevTools-like DOM / CSS / input / performance operations, and can ask the user to pick elements or answer questions. Carriers cover Vite / webpack / Nuxt / Astro, plus a browser extension (any site) and a VS Code extension, all on one bridge protocol. Page injection is not exclusive — any MCP host can use aiti-bridge; here it is simply a built-in panel, sharing the same origin as the workbench. The experimental area keeps growing: CodeHub brings work items and repositories in, Video Studio turns demo videos into a repeatable pipeline, and Model Gateway lends configured models to external agents — all still in beta (see §2.6). See aiti-devtools.

Compatibility is what makes this work: the pi CLI, the pi IDE extension and the web operate on the same session files, not three separate stores. You do not have to pick a side.

6. Ten-minute self-test

Skip the prose and just do this:

  1. Start it: npx --allow-scripts=@aiti-ai/pi-web @aiti-ai/pi-web@latest (or docker run -d -p 30142:30142 aitiai/pi-web:core).
  2. Open two agents: create a pi session, then attach an installed, logged-in Claude Code / Codex session from the sidebar; confirm both live in one project tree.
  3. Switch devices: open the same URL on a phone (or through a tunnel), send a message, queue one, switch the model.
  4. Close the browser: wait 30 seconds and reopen; the agent has not stopped and the output is still there.
  5. Restart the service: docker restart or systemctl restart, then reopen the session; on backends that support detached mode the agent replays its history and continues.
  6. Read the numbers: open the usage report, pivot by provider / model, export a CSV.
  7. Enter the page: add @aiti-ai/aiti-devtools-vite to any Vite project and ask the AI to restyle an element you click.

If three or more of these feel like something you would use daily, the web workbench is the right center. If only step 7 resonates, you probably need aiti-devtools rather than the whole workbench. If none of them do, do not migrate — the tool that fits your hand beats the one with more features.
